# H3 · Схема БД и миграции

## Зачем блок нужен

`src/shared/db/` — 3,5 тыс. строк, из них 3 тыс. — `schema.ts`: 87 таблиц, 86 индексов, 64
уникальных ограничения, 29 enum'ов, 41 колонка jsonb. Всё остальное приложение обращается
к базе через этот слой, и ошибка здесь не локальна: несовпадение цели `onConflict` с
уникальным ограничением роняет запись в рантайме, индекс не той формы молча отдаёт ленту
через seq scan, а сырое `sql\`\`` переживает переименование колонки, потому что компилятор в
строку не смотрит. Миграции (`drizzle/`, 48 файлов) в проекте МЕРТВЫ с #334: схема
накатывается только `drizzle-kit push` (CI, `db:init`, прод), и AGENTS.md §8 запрещает
`generate`. Блок должен сказать, где схема и код разошлись, а не спроектировать схему заново.

## Что считается находкой, а что нет

**Находка:** цель `onConflict`, под которой нет уникального ограничения; запрос с
`orderBy`/keyset, под которым нет индекса нужной формы (или он есть, но с другим `NULLS`);
сырое SQL-выражение, называющее колонку/значение enum'а, которых в схеме нет; jsonb, чья
форма при записи отличается от `$type` при чтении; настройка пула, при которой неверный
env молча превращается в дефолт; FK без `onDelete`, на каскад которого код рассчитывает;
мёртвая команда (`db:migrate`, `db:generate`), способная сломать базу тому, кто её вызовет.

**Не находка:** «таблиц слишком много», «стоило бы нормализовать», «имя колонки неудачное».
Замечания к производительности принимаются только с формой запроса и индекса, а не с
ощущением: пользователей почти нет, числа наблюдать не на ком.

## Гипотезы, специфичные для проекта

1. **Цель `onConflict` без уникального ограничения.** В коде 53 вызова `onConflict*`;
   десять разных целей (`listDrafts(templateId, authorId)`, `templateViews(templateId,
   visitor, day)`, `knowledgeTriples` по четырём колонкам, `quizAttempts` по трём и т. д.).
   Гипотеза: хотя бы одна цель не совпадает с `unique`/PK в `schema.ts` по составу или
   порядку колонок — Postgres ответит `no unique or exclusion constraint matching`, и
   ответит только в рантайме, на первом конфликте.
2. **Keyset без индекса той же формы.** `keyset.ts` требует индекс `(…, key DESC, id DESC)`
   с `NULLS FIRST`; узда `tests/architecture/index-nulls-order` проверяет это по СПИСКУ,
   заданному руками. Девять поверхностей используют keyset. Гипотеза: у одной из них индекса
   нет, нет `id` в хвосте, либо она не попала в список узды и та её не видит (§H1-11: та же
   болезнь у `READ_ONLY`).
3. **Сырой SQL пережил схему.** 89 файлов вне слоя используют `sql\`\``; в строках —
   имена колонок и значения enum'ов литералами. Гипотеза: есть строка, называющая колонку
   или значение, которых в `schema.ts` уже нет (переименовано/удалено), либо значение
   enum'а с опечаткой — TypeScript такого не ловит.
4. **Дата из сырого выражения мимо `asDate`.** `raw.ts` заведён после падения 13.08
   («getTime is not a function»). Гипотеза: остался `sql<Date…>` с прямым `.getTime()` /
   сравнением, не пропущенный через `asDate`.
5. **Пул: неверный env молча превращается в дефолт.** `max: Math.max(10, DB_POOL_MAX||20)`
   — `DB_POOL_MAX=5` станет 10 без слова; `DB_POOL_MIN=30` при `max=20` — что сделает `pg`?
   Гипотеза: нарушено правило 7 (тихая деградация) — конфигурация принимается и не
   действует. Отдельно: `idleTimeoutMillis` не задан, воркер и веб делят один пул.
6. **`db` в проде строится на каждое обращение.** `index.ts`: `global.__pgDb` кэшируется
   только вне `production`; `Proxy.get` зовёт `getDb()` на КАЖДОЕ свойство, то есть на
   проде `drizzle(pool, { schema })` создаётся при каждом `db.select`/`db.transaction`.
   Гипотеза: это так, и цена — не только объект: у drizzle есть состояние (логгер, кэш
   схемы), которое каждый раз строится заново. Проверить чтением, замерить не нужно.
7. **Метод через Proxy теряет `this`.** `get` возвращает `real[prop]` без `bind`;
   `db.transaction(cb)` вызывается с `this === proxy`. Гипотеза: работает случайно —
   потому что нужные методы drizzle не зависят от `this`, — и любой метод, который
   зависит, упадёт. Найти хотя бы один такой или доказать, что их нет.
8. **Регистр ника в резолве.** `resolveListBySlug` сравнивает `eq(users.handle, owner)`
   как есть. Гипотеза: либо ник хранится в одном регистре и адрес нормализуется до запроса
   (тогда где — и покрывает ли это `[...git]`-роут и MCP), либо `/Miki/list` и
   `/miki/list` — два разных списка для базы и один для человека. Сверить с уникальным
   индексом на `handle` (`lower()`?) и `userRedirects`.
9. **Цепочка переездов.** `listRedirects`/`userRedirects`: A→B, потом B→C. Гипотеза:
   `resolveListOrMoved` идёт на один шаг, и адрес A после второго переезда ведёт на
   несуществующий B (Gitea при переезде переписывает старые редиректы на новую цель).
   Отдельно: редирект с ника, который спустя 180 дней занял другой человек, — кто его
   удаляет и есть ли ограничение, не дающее `from` совпасть с живым `handle`.
10. **Каскад, которого нет в схеме.** Гипотеза: есть `references()` без `onDelete`, при
    этом код удаления пользователя/списка не чистит зависимую таблицу сам — удаление
    падает на FK либо оставляет сирот (проверить по одной таблице на каждую сторону:
    `templates`, `users`).
11. **Jsonb: писатель и `$type` разошлись.** 41 колонка jsonb. Гипотеза: у колонки нет
    `$type` вовсе, либо тип уже, чем то, что туда пишут (правило 2: тихая потеря полей на
    чтении). Начать с `generation_candidates.items`, `templates.blocks`, полей настроек.
12. **Курсор keyset приводится к `timestamptz` для ключа другого типа.** Гипотеза: есть
    поверхность с числовым или текстовым ключом (`score`, `handle`), где приведение из
    `keyset.ts` не совпадает с типом колонки.
13. **Мёртвые команды миграций.** `db:generate` и `db:migrate` лежат в `package.json`, хотя
    §8 AGENTS.md запрещает первую, а миграции устарели с #334 (48 файлов, `drizzle/**`
    исключён из чтения — судить по `git log`, не по содержимому). Гипотеза: команда
    работает и ломает базу; узды, не дающей её вызвать, нет — правило 3, «мёртвое право».
14. **`templateViews.day` и часовой пояс.** День считается в приложении или в базе?
    Гипотеза: граница суток зависит от TZ процесса, и одна и та же минута до/после полуночи
    по UTC даёт два разных `day` в двух репликах — узда `day-boundary.yml` проверяет иное.

## Критерий приёмки

Блок не закрывается без трёх таблиц, собранных чтением кода:

1. **`onConflict` → ограничение.** Все 53 вызова: файл, цель, уникальное ограничение в
   `schema.ts`, совпадение по составу и порядку. Проверяющий пересобирает независимо.
2. **Лента → индекс.** Девять поверхностей keyset и `orderBy` с `limit` на горячих путях
   (витрина, поиск, уведомления, обсуждения): колонки порядка, индекс, `NULLS`, наличие
   в списке узды `index-nulls-order`.
3. **Сырое SQL → схема.** По 89 файлам: идентификаторы из `sql\`\``-строк, которых нет в
   `schema.ts` (пустая таблица — тоже результат, но только с описанием, как искали).

Гипотезы 6–7 (Proxy) — либо находка с доказательством, либо явное «проверено, `this` не
нужен, потому что …» в «Границах охвата».
