# Сплошное ревью SetFork

Состояние ревью живёт **на диске, а не в переписке**. Сессия, которая ничего не знает,
выполняет одну команду и видит полную картину.

```sh
npm run review:status     # где мы и какой блок следующий
npm run review:coverage   # карта «файл → блок»; падает, если файл ничей
npm run review:check      # манифесты на месте, шаблоны путей не пустые, гипотезы закрыты
npm run review -- hypotheses H1             # что из гипотез блока закрыто, а что висит
npm run review -- prompt H1 --role hunter   # готовый промпт агенту
```

## Устройство

| файл | что это |
|---|---|
| `blocks.json` | из чего состоит ревью: 28 блоков, их файлы. Правится руками |
| `state.json` | как далеко зашёл каждый блок. Правится инструментом |
| `invariants.md` | **правила SetFork.** Вклеиваются каждому агенту; от них зависит, что он сочтёт дефектом |
| `blocks/<ID>-<слаг>.md` | манифест блока: зачем, что находка, гипотезы, критерий приёмки |
| `findings.jsonl` | реестр находок, по строке на находку |
| `coverage.tsv` | карта покрытия, пересобирается |
| `prompts/<роль>.md` | **необязательно.** Своя версия шаблона роли — берётся вместо скилловой. Сейчас своих нет: три роли (охотник, проверяющий, исполнитель) идут из скилла `.claude/skills/review-kit/references/` |

## Порядок работы над блоком

1. **Манифест.** Написать `blocks/<ID>-<слаг>.md` — без проектных гипотез ревью выйдет «по
   общим соображениям». Образец: `blocks/H1-access.md`.
2. **Охотник** (`--role hunter`) читает файлы блока и выдвигает находки. В отчёте обязательны
   **вердикты по всем гипотезам** манифеста («проверена / не проверена / неприменима») и раздел
   про то, что осознанно не смотрел: карта файлов отвечает «файл открывали», а гипотезы — «на
   вопрос получен ответ». Это второй знаменатель покрытия, и `check` требует его наравне с картой.
3. **Проверяющий** (`--role verify`) проверяет каждую по текущему коду и делает свой
   независимый проход. Отвергнутые находки **не удаляются** — остаются с причиной отказа,
   иначе следующее ревью найдёт то же самое.
4. **Приёмка.** Прочитать отчёты самому и сверить с критерием приёмки блока. Охват неполный —
   вернуть на повторный проход, а не закрывать.
5. **Починка** (`--role fix`) — **другим** агентом, не тем, кто искал.
6. **Ревью диффа** — теми, кто его не писал, **до** открытия предложения.

⚠️ Один агент не ищет и не чинит одновременно. ⚠️ Блок не закрывается без выполненного
критерия приёмки.

## Три фазы

**Сквозные** (H1–H13) идут первыми: они задают язык. Когда блок доступа выписал таблицу
«маршрут → гейт», доменные блоки читают код, уже зная границы.
**Доменные** (V1–V12) читают свой срез целиком — от миграции до экрана.
**Стендовые** (S1–S3) файлами не владеют: работают на запущенной системе.

## Как это заканчивается

Когда блоки закрыты и открытых находок нет, `docs/review/` **удаляется целиком одним
предложением**, а долговечное переезжает туда, где живёт по-настоящему: правила — в
`CONTRIBUTING.md` и `AGENTS.md`, решения — в HQ, проверки — в тесты и узды CI. Каталог ревью
— это леса вокруг стройки, а не часть здания.

Инструмент и шаблоны ролей — скилл **review-kit** по стандарту Agent Skills
([github.com/mikey-semy/review-kit](https://github.com/mikey-semy/review-kit)); основоположник
метода — [Георгий Худобандаев](https://github.com/Georgiy-Khudobandaev). Копия в
`.claude/skills/review-kit/` закоммичена намеренно — она закрепляет версию, источник записан в
`skills-lock.json`. Обновление: `npx skills add mikey-semy/review-kit -a claude-code --copy`,
затем `npm run review:check` — новые проверки находят старые ошибки реестра.

## Сколько это стоит

Оценка до первого нашего прогона, по фактам соседнего проекта (`arch-dashboard`, 13 блоков).
⚠️ Токены там **не логировались** — известно число агентов и размеры блоков; расход на агента
взят по карте агентов владельца (300–450 тыс.) и помечен как косвенный.

**Главное: 15 агентов на блок — худший случай, а не типичный.**

| | агентов | где это было |
|---|---:|---|
| обзор: охотник + верификатор, чинить нечего | **2** | H2…H8 — семь блоков из тринадцати |
| блок, где ломается: 3 круга «починил → прочитали дифф» | **12** | H1, один блок из тринадцати |

Разницу в шесть раз решает **не размер блока, а наличие регрессий в починке**. Самое дорогое —
круги починки, а не чтение: охотник читает один раз, исполнитель читает, правит и гоняет
тесты — и так шесть раз.

**Пересчёт на нас.** Считать надо не «39 × 15», а по двум ставкам. Если доля чинимых блоков
та же (один из тринадцати), выходит `39×2 + 3×10 ≈ 108 агентов`, то есть **порядка 30–35 млн
токенов** — а не 90, как я прикинул сначала.

⚠️ Поправка в другую сторону: их блоки **втрое-вчетверо мельче наших** (H1 — 2210 строк,
H2 — 749). Наши двенадцать блоков сверх порога 6000 строк обойдутся дороже обзорной ставки,
пока не разрезаны. Это ещё один довод резать их до прогона, а не после. (Разрезаны 21.09:
блоков стало 67, крупнейший — 5 938 строк.)

**⚠️ ПОРОГА СНИЗУ НЕТ, И ЭТО СОЗНАТЕЛЬНО.** Размер блока — следствие темы, а не мерило
работы. Блок обязан отвечать на ОДИН вопрос, и если ответ короткий, это свойство вопроса, а
не недоделка: у сквозных блоков своих файлов мало (H9 «Сессии, токены и заголовки» — пять),
потому что сессии живут в пяти файлах, а проверяет такой блок весь код на предмет того, кто
их трогает. Слить его с соседом значит смешать два правила в одном отчёте — и потом не
понять, какое из двух проверено.

Сливать стоит только блоки, отвечающие на ОДИН И ТОТ ЖЕ вопрос. Так слиты «настройки и
опасные действия» с «блоками и правкой содержимого»: оба про экранную правку списка.

**Порядок работы, который там сработал:** сначала одним заходом прогнать обзором все блоки,
где чинить нечего — они закрываются двумя агентами и больше не трогаются. Дорогие круги
растянуть по неделям и вести только там, где дефект дорого стоит.

**Правило остановки задаётся заранее и не по числу находок, а по их роду.** У них сходимость
была 11 → 4 → 4: число встало, но останавливались, когда к третьему кругу ни одна находка не
была про порчу файла. Наше правило: сливаем, когда у авто-ревью нет P1, а у проверяющего нет
находок выше низкой.

**Первые по риску** (там дефект необратим или стоит чужих денег): `H1` доступ и видимость,
`H15` доменное ядро, `V1d` запись и версии, `H5` деньги и квоты, `H4` поверхность MCP.
