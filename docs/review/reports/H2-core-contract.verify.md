## Разбор находки №9 — проверено в обе стороны

### Половина первая: сторож слеп. ДОКАЗАНО МУТАЦИЕЙ.

Вставил в `src/features/zzfake/rogue.ts` новый маршрут, создающий версию в ядре обоими
способами и без всякой базы:

```ts
const a = await gitCore.mergeBranch({ owner, slug }, branch, { mode: 'squash' })
const b = await gitCore.mergeResolved({ owner, slug }, branch, { …, version: 999, steps: [] })
```

`npx vitest run tests/architecture/version-base-declared.test.ts` → **12 passed**. Сторож
не покраснел ни на йоту. Он сканирует `callArgs(text, 'listStore.addVersion(')`, а эти два
маршрута фасад не зовут вовсе; в `ROUTES` шесть файлов, и по построению седьмым там может
стать только ещё один вызывающий фасада. Докблок при этом обещает ловить «ПОЯВЛЕНИЕ
девятого маршрута мимо решения» — мутация показывает, что «мимо решения» он читает как
«мимо таблицы», а не «мимо фасада». (Попутно: докблок говорит «маршрутов восемь», а вызовов
`listStore.addVersion(` в `src/` ровно **шесть**.)

Файл удалён, дерево возвращено в чистоту.

### Половина вторая: числа действительно расходятся — и БЕЗ гонки.

Обе стороны прочитаны:

* `convert.rs: from_list_content` → `version: c.version` — число с провода попадает в
  `VersionData` дословно;
* `serialize.rs: list_json` → `root.insert("version", …)` — и дословно уезжает в канон
  отдельной строкой pretty-JSON;
* `project.rs: project_pushed_commit` → `let ver = db::add_version(…)`, и `parsed.version`
  для нумерации НЕ используется вовсе;
* `db/write.rs: add_version_rows` → `select current_version … for update` → `current + 1`;
* `project.rs:395` → `tag_version(bare, ver, tip)` вешает `vN` на тот самый коммит.

То есть номер в теге и номер внутри `list.json` одного коммита считаются двумя независимыми
механизмами, и сверки между ними нет нигде — это прямо признано в нашем же коде
(`suggestion-branch.ts:224`: «`tpl.currentVersion + 1` — это то, что мы ПОПРОСИЛИ, а
записать могли другое»).

**Но гонка для расхождения не нужна.** Число попадает в ветку гораздо раньше резолвера:
`writeSuggestionItems` (`suggestion-items.ts:109`) пишет в ветку
`version: tpl.currentVersion + 1` при КАЖДОЙ правке пунктов. Дальше main живёт своей
жизнью. Прогнал настоящим git на трёх файлах, отличающихся только этой строкой
(`git merge-file`, база = коммит развилки):

| main ушёл вперёд на | исход слияния | что получилось |
|---|---|---|
| 1 версию | **чисто, exit 0** | в `list.json` остаётся `"version": 6`, проекция создаёт версию 7 и вешает `v7` — **канон врёт о своём номере, и никакой гонки для этого не нужно** |
| 2 версии и больше | **конфликт, exit 1** | `<<<<<<<` ровно на строке `"version"`, при полностью совместимом содержимом |

Сценарий охотника (соавтор публикует, пока владелец разбирает конфликты) тоже возможен, но
он лишний: расхождение штатно получается на самом обычном пути «поправил пункты правки →
владелец успел опубликовать версию → влили».

**Вывод по №9: ПОДТВЕРЖДЕНА целиком, severity medium.** Сама по себе неверная цифра в
`list.json` — порча витрины, а не данных: Postgres, теги и история правы. Но вторая строка
таблицы выше — это уже не витрина, и я выношу её отдельной находкой.

## Собственные находки

### H2-V01 · high · Правка застревает навсегда: git конфликтует по номеру версии, а продукт этого конфликта не видит и показать не может
**Место:** `src/features/library/actions/suggestion-items.ts:109` (источник числа),
`src/app/[handle]/[slug]/suggestions/[id]/load.ts:163` (свой трёхсторонний разбор),
`setfork-core/src/services/git_core/mod.rs` (`merge_branch`, `update_branch`)

**Что не так.** Номер версии — единственное поле канона, которое фронт ПРЕДСКАЗЫВАЕТ, а
владеет им ядро. Предсказание замерзает в `list.json` ветки. Когда main уходит вперёд на две
версии и больше, обычный текстовый three-way по этой строке даёт конфликт (доказано выше,
`git merge-file` exit 1) — при том, что по существу стороны не спорят.

Дальше продукт заходит в тупик:

* `mergeBranch` → `repo.merge_commits` → `idx.has_conflicts()` → `BranchOpError('conflict')`
  (mod.rs). То же на `mode: "squash"` — squash считает дерево тем же merge-ом;
* «Обновить из main» не спасает: `update_branch` (mod.rs:789–796) делает ровно тот же
  `merge_commits` и падает тем же `Conflict`;
* резолвер НЕ предлагается: `hasConflicts` считается СВОИМ разбором по снимкам
  (`load.ts:159–163`), а `BranchSnapshot` поля `version` не несёт вовсе — семантических
  конфликтов нет, значит `hasConflicts === false` и `ConflictResolver` не рендерится
  (`SuggestionConversation.tsx:242`);
* повторная правка пунктов не помогает: она пишет `currentVersion + 1`, то есть снова
  число, отличное от main.

**Сценарий отказа.** Автор правит пункты своего предложения через веб-редактор. Владелец
за это время публикует две версии. Автор и владелец жмут «Влить» — «конфликт». Жмут
«Обновить из main» — «конфликт». Формы разрешения конфликтов на странице нет, потому что
разрешать, с точки зрения продукта, нечего. Выход есть только мимо продукта: пушем из
терминала поправить одну строку в `list.json`. Работа не потеряна (она в git), но путь в
интерфейсе мёртв.

**Почему дефект.** Это цена находки №9, выраженная не в неверной цифре, а в
неработающем действии: предсказанное число стало частью содержимого, по которому git
считает согласие сторон. Инвариант 7 плюс «кнопка выглядит сломанной».

**Чем чинить (направление, не задание исполнителю).** Номер версии в `list.json` обязан
проставлять тот, кто его назначает, — ядро, при сборке канона, из своего же
`current_version` под тем же локом. Поле `ListContent.version` тогда становится тем же, чем
уже стали `danger`/`imageKey`: полем, которое на записи игнорируется. Это заодно закрывает
и №9.

**Уверенность:** confirmed (обе стороны прочитаны, поведение git проверено прогоном;
на живом стенде не воспроизводил).

### H2-V02 · low · Сторож «база правки» не проверяет сам себя на маршрутах мимо фасада
**Место:** `tests/architecture/version-base-declared.test.ts:78`

Отдельно от №9 — про форму узды, а не про версию. У сторожа есть контроль «сканер вообще
видит маршруты» (`found.length >= ROUTES.length`), и он честно ловит «сканер смотрит не
туда» ВНУТРИ своего признака. Признака «версию создали в ядре» у него нет ни одного, и
отсутствие такого признака ничем не обнаруживается: мутация выше зелёная. Пока второй
признак не заведён, докблок обязан называть границу прямо («маршруты ЧЕРЕЗ ФАСАД»), иначе
следующий читающий примет зелёный сторож за доказательство, что мимо фасада версий не
создают.
