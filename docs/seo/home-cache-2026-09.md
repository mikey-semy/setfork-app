# Кеширование главной: разбор, а не правка

Работа 6 из `seo-audit-2026-09.md`. Наряд прямо требовал **не править вслепую**: сначала
выяснить, различается ли главная для гостя и вошедшего, и записать вывод.

**Вывод: запрет кеширования оправдан, менять нечего.** Ниже — почему, с замерами.

## Что наблюдается

```
cache-control: private, no-cache, no-store, max-age=0, must-revalidate
```

⚠️ Заголовок ставит **не наш код**. В `middleware.ts` `no-store` есть только у режима
ремонта и машинных ответов; на главной его выставляет Next, потому что страница читает
куки (сессия и язык). То есть это следствие устройства страницы, а не отдельное решение,
которое можно «отменить настройкой».

## Причина первая: для вошедшего это ДРУГАЯ страница

`src/app/page.tsx`:

```ts
const [lang, session] = await Promise.all([getLang(), getSession()])
if (session) return <Dashboard lang={lang} userId={session.userId} />
```

Не «лендинг с персонализированным блоком», а полная подмена: вошедший получает личный
дашборд со своими списками. Отдать общий закешированный ответ нельзя в принципе — гость
получил бы чужой дашборд либо вошедший увидел бы лендинг вместо своих дел.

## Причина вторая: даже для гостя страница различается

Аудит предполагает, что «для гостя она одинакова». Это неверно.

Плейсхолдер поиска выбирается случайно из пула, а подсказки под строкой — живые заголовки
списков из базы. Два запроса подряд к проду, 22.09.2026:

```
заход 1: placeholder="Find a proven list…"
заход 2: placeholder="What needs doing — step by step?"
```

Закешировать это значит зафиксировать один случайный вариант на срок жизни кеша — и
подсказки перестанут показывать то, что в библиотеке появилось сегодня.

## Причина третья, решающая: экономить нечего

Замер прода, пять заходов подряд, время до первого байта:

| что | время до первого байта |
|---|---|
| главная (собирается на каждый заход) | 0.176 · 0.166 · 0.160 · 0.175 · 0.158 с |
| `robots.txt` (полностью статический) | 0.158 с |

**Разница между динамической главной и статическим файлом — в пределах шума сети.**
Сборка страницы стоит порядка десяти-двадцати миллисекунд из ста шестидесяти; остальное —
дорога до сервера. Кеширование выиграло бы эти миллисекунды и проиграло бы свежесть
подсказок.

Поведенческие факторы, ради которых аудит и поднимает вопрос, на такой разнице не
двигаются: человек её не замечает.

## Что было бы, если бы мы всё-таки захотели кешировать

Записано на случай, если главная изменится и вопрос вернётся. Это продуктовое решение,
а не техническое:

1. **Развести адреса.** Лендинг остаётся статическим на `/`, вошедший уводится на
   отдельный адрес дашборда (`/home` или `/my`) редиректом в middleware. Тогда `/`
   кешируется целиком и отдаётся с CDN.
2. **Случайность — на клиент.** Плейсхолдер выбирается в браузере, а не на сервере;
   страница перестаёт различаться между заходами.
3. **Подсказки — с ревалидацией.** Живые заголовки списков берутся с `revalidate: 300`
   вместо запроса на каждый заход: свежесть в пять минут против свежести в секунду.

Цена: три изменения в поведении продукта ради выигрыша, который в замере не виден.
Поэтому сейчас не делается.

## Как перепроверить, если что-то изменится

```bash
# страница для гостя и для вошедшего — одна и та же или разные?
grep -n "if (session) return" src/app/page.tsx

# различается ли ответ между заходами
curl -s https://setfork.com/ | grep -o 'placeholder="[^"]*"'   # дважды, сравнить

# сколько стоит сборка: главная против статического файла
curl -s -o /dev/null -w "%{time_starttransfer}\n" https://setfork.com/
curl -s -o /dev/null -w "%{time_starttransfer}\n" https://setfork.com/robots.txt
```
