# Бэкапы и восстановление (runbook)

Что бэкапим, как и как восстановить. Скрипты: [`scripts/backup.sh`](../scripts/backup.sh),
[`scripts/restore.sh`](../scripts/restore.sh).

## Что входит в бэкап

| Стейт | Где живёт | Как бэкапится | Критичность |
|---|---|---|---|
| **Postgres** | том `pgdata`, сервис `db` | `pg_dump -Fc` (логический, сжатый) | высокая — вся метадата, юзеры, issues, токены |
| **git-данные** | ⚠️ том `setfork_git` в проекте **setfork-core** (не здесь) | `tar czf` тома | высокая — источник правды bare-репозиториев списков |
| Медиа (аватары/вложения) | S3 (Selectel/MinIO) | реплика на стороне S3 | средняя — вне этого скрипта |

Почему **логический** дамп Postgres, а не снапшот тома: `pg_dump -Fc` восстанавливается
на любой pg16+, переживает смену минорной версии и частичный рестор. Снапшот тома
привязан к точной версии кластера.

Медиа намеренно не в скрипте: оригиналы лежат в S3 с собственной надёжностью/репликацией.
Если развёрнут **свой** MinIO (том `miniodata`) — добавьте его tar по образцу git-тома.

## RPO / RTO

- **RPO** (сколько данных теряем): при ежедневном cron — до 24 ч. Нужно меньше — чаще запускать
  или включить WAL-archiving (вне рамок этого runbook).
- **RTO** (сколько восстанавливаемся): минуты — рестор упирается в размер дампа и tar.

## Расписание

`backup.sh` не демон — вешается на cron прод-хоста:

```cron
# ежедневно 03:15 UTC
15 3 * * *  cd /root/setfork/src/setfork-frontend && COMPOSE_FILE=docker-compose.dokploy.yml ./scripts/backup.sh >> /var/log/setfork-backup.log 2>&1
```

Переменные: `COMPOSE_FILE`, `BACKUP_DIR` (по умолч. `./backups`), `RETENTION_DAYS` (14),
`PROJECT` (имя compose-проекта — влияет на имя тома `<project>_gitdata`).

## Offsite — обязательно

Локальные бэкапы на том же хосте не спасают от потери хоста. В `backup.sh` есть
закомментированный `rclone copy` — настройте remote (S3/B2/другой регион) и раскомментируйте.
Правило 3-2-1: 3 копии, 2 носителя, 1 offsite.

## Восстановление

Деструктивно — перезаписывает БД и git-том. Требует ввести `YES`.

```sh
# по метке из имени файлов (db-<TS>.dump / git-<TS>.tar.gz)
COMPOSE_FILE=docker-compose.dokploy.yml ./scripts/restore.sh 20260704-031500Z
# либо явными путями
./scripts/restore.sh ./backups/db-….dump ./backups/git-….tar.gz
```

Скрипт: останавливает `app`+`core` (чтобы никто не писал) → `pg_restore --clean` →
очищает и распаковывает git-том → `docker compose up -d`.

## Проверка бэкапа (делать ежемесячно — иначе это не бэкап)

Бэкап без проверенного рестора — иллюзия. Раз в месяц прогоняйте на отдельном хосте/проекте:

1. Скопировать свежие `db-*.dump` + `git-*.tar.gz` на тестовый хост.
2. Сверить контрольные суммы: `sha256sum -c manifest-<TS>.sha256`.
3. `COMPOSE_PROJECT_NAME=setfork_restoretest ./scripts/restore.sh <TS>`.
4. Открыть `/admin` (данные на месте) и `git clone http://<host>/<handle>/<slug>.git` одного
   из списков — репозиторий клонируется и содержит историю.
5. Снести тестовый проект: `docker compose -p setfork_restoretest down -v`.

Записать дату успешной проверки — если давно не проверяли, считайте, что бэкапа нет.
