# Dev-сервер отдельным юнитом: падать должна сборка, а не редактор

22.09.2026 замер памяти на редакторе длинного списка утащил **весь VS Code**: dev-сервер
дорос до 7,3 ГБ и машина начала выгружать всё остальное. Правка кода тут не поможет —
нужен предел, который ставит система.

## Течёт и JS-куча, и нативная часть — поэтому средства ДВА

Замеренный предел V8-кучи по умолчанию на этой машине — **4288 МБ**:

```
node -e "console.log(require('v8').getHeapStatistics().heap_size_limit/1048576)"
→ 4288
```

⚠️ **Здесь стояло утверждение, что `--max-old-space-size` эту утечку не ловит. Оно
неверно, и проверка это показала.** Рассуждение было такое: процесс вырос до 7,3 ГБ, а
предел кучи 4,3 ГБ, значит растёт нативная часть Turbopack и флаг до неё не достаёт.
Вывод сделан из одного числа, без прогона.

Прогон 22.09.2026 с `NODE_OPTIONS=--max-old-space-size=2048` на редакторе списка в 120
пунктов:

```
[2311694] 337161 ms: Mark-Compact 1980.1 (2073.4) -> 1963.8 (2071.9) MB
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
```

Куча дошла до **1980 МБ** и упёрлась в поставленный предел за пять с половиной минут.
Процесс упал сам, **редактор остался жив** — то есть флаг работает и делает ровно то, ради
чего ставился.

Значит **течёт и JS-куча тоже**: два гигабайта на списке из 120 пунктов — не норма.
Наблюдавшиеся 7,3 ГБ, видимо, складывались из кучи (до дефолтных 4,3) и нативной части
сверху. Оба средства нужны, и ни одно не заменяет другое:

- флаг V8 ограничивает **JS-часть** — как выяснилось, именно она и упирается первой;
- `MemoryMax` в юните ограничивает **всю** память процесса, включая нативную, и остаётся
  единственным средством против роста вне кучи.

⚠️ И он **не работает из `.env`**: Next читает `.env` своим загрузчиком уже внутри
запущенного процесса, а флаги V8 применяются при старте. Проверено: через `node --env-file`
предел меняется (Node читает файл до старта), через `.env` приложения — нет. Поэтому флаг
живёт в скрипте `dev` в `package.json`.

## Юнит

```ini
# ~/.config/systemd/user/setfork-dev.service
[Unit]
Description=SetFork dev server (Next 16)
After=network.target

[Service]
Type=simple
WorkingDirectory=/home/mike/Projects/setfork-app
ExecStart=/usr/bin/npm run dev
Restart=on-failure
RestartSec=2

# ⚠️ Главная строка. MemoryMax считает ВСЮ память процесса и потомков, включая нативную
# часть Turbopack — в отличие от предела V8-кучи. При превышении ядро убивает только этот
# срез, редактор и остальные процессы не затрагиваются.
MemoryMax=3G
# Заранее поджимать, не дожидаясь жёсткого предела: рост замедляется, и часто до убийства
# дело не доходит вовсе.
MemoryHigh=2500M
# Своя группа — чтобы `systemctl --user status` показывал, что именно упало и почему.
Slice=dev.slice

[Install]
WantedBy=default.target
```

## Как пользоваться

```bash
systemctl --user daemon-reload
systemctl --user start setfork-dev        # запустить
journalctl --user -u setfork-dev -f       # смотреть лог вместо терминала VS Code
systemctl --user status setfork-dev       # после падения: что случилось и по какой причине
```

Убийство по памяти выглядит в статусе так — это ответ на вопрос «почему упало»:

```
Main PID: … (code=killed, signal=KILL)
Memory: 3.0G (max: 3.0G available: 0B)
```

## Что это даёт и чего не даёт

**Даёт:** падает только сборка, окно редактора живо; видно, что упало именно по памяти, а не
«само закрылось».

**Не даёт:** причину роста. Её ищут снимком памяти отдельно — и до сих пор она не найдена:
известно только ГДЕ искать (куча next-server растёт до 2 ГБ за 5,5 минут на 120 пунктах) и
что рост не останавливается сам.

⚠️ **Ловушки, на которых легко потерять час** (все случились 22.09):

1. **Два dev-сервера в одном дереве** дёргают HMR друг против друга, и вкладка
   перезагружается по кругу — со стороны выглядит как утечка или сломанная правка.
2. **`pkill -f "next dev"` убивает собственную оболочку**, потому что её командная строка
   содержит ту же подстроку; серверы при этом переживают. За день это случилось трижды —
   признак в логе один: команда обрывается с кодом 144, а процессы на месте.

⚠️ **`pgrep -x next-server` не находит НИЧЕГО**, хотя выглядит правильным решением. Имя
процесса в `/proc/<pid>/comm` обрезано ядром до 15 символов, а Next пишет туда версию:

```
pid 1965687 → comm: «next-server (v1»   (не «next-server»!)
pgrep -x next-server → 0 процессов
pgrep -f  next-server → 5 процессов (включая собственную команду)
```

Рабочий способ — искать по `-f`, но отсеивать себя, предка и чужие каталоги, а `comm`
сверять **по префиксу**:

```bash
me=$$; parent=$(ps -o ppid= -p $me | tr -d ' ')
for p in $(pgrep -f next-server); do
  [ "$p" = "$me" ] || [ "$p" = "$parent" ] && continue
  case "$(cat /proc/$p/comm)" in next-server*)
    [ "$(readlink /proc/$p/cwd)" = "$PWD" ] && kill "$p" ;;
  esac
done
```

Через юнит этой возни нет вовсе: `systemctl --user stop setfork-dev` гасит ровно свой срез.
3. **Кэш `.next` после падения по памяти остаётся битым**: страница отдаётся, но части
   разметки в ней нет вовсе, хотя код на месте. Лечится только `rm -rf .next`.

## Как повторить замер

Полного профиля памяти пока нет — известна одна точка (2 ГБ кучи за 5,5 минут на 120
пунктах). Стенды для остальных уже созданы: списки `mem-bench-5 / 30 / 60 / 120 / 240` у
пользователя `membench`, то есть кривую по размеру можно снять сразу, а не гадать по одной
точке.

Вход на стенде — подделанной сессией (строка в `sessions` + JWT-кука на `AUTH_SECRET`),
Playwright берётся из соседнего проекта `setfork-sim`. ⚠️ Ходить на `localhost`, а не на
`127.0.0.1`: по IP Next в dev режет собственные ресурсы, гидрация не доезжает, и со стороны
это неотличимо от сломанной правки.

⚠️ Запускать этот замер **не одновременно с CI**: раннеры живут на той же машине, и
Playwright с браузером тяжелее всего набора тестов. 22.09 три предложения упали красными
именно из-за этого — в логе `The runner has received a shutdown signal`, что выглядит как
чьё-то вмешательство, а не как нехватка памяти.
