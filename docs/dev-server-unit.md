# Dev-сервер отдельным юнитом: падать должна сборка, а не редактор

22.09.2026 замер памяти на редакторе длинного списка утащил **весь VS Code**: dev-сервер
дорос до 7,3 ГБ и машина начала выгружать всё остальное. Правка кода тут не поможет —
нужен предел, который ставит система.

## Почему `NODE_OPTIONS=--max-old-space-size` эту задачу не решает

Замеренный предел V8-кучи по умолчанию на этой машине — **4288 МБ**:

```
node -e "console.log(require('v8').getHeapStatistics().heap_size_limit/1048576)"
→ 4288
```

Процесс вырос до **7,3 ГБ**. Если бы тёк JavaScript, он упал бы сам на 4,3 ГБ. Значит
рост шёл **вне V8-кучи** — в нативной части Turbopack (Rust), который в Next 16 работает
в dev по умолчанию. `--max-old-space-size` до неё не достаёт.

Флаг всё равно стоит держать — он ограничивает JS-часть и делает падение предсказуемым, —
но одного его мало.

⚠️ И он **не работает из `.env`**: Next читает `.env` своим загрузчиком уже внутри
запущенного процесса, а флаги V8 применяются при старте. Проверено: через `node --env-file`
предел меняется (Node читает файл до старта), через `.env` приложения — нет. Поэтому флаг
живёт в скрипте `dev` в `package.json`.

## Юнит

```ini
# ~/.config/systemd/user/setfork-dev.service
[Unit]
Description=SetFork dev server (Next 16)
After=network.target

[Service]
Type=simple
WorkingDirectory=/home/mike/Projects/setfork-app
ExecStart=/usr/bin/npm run dev
Restart=on-failure
RestartSec=2

# ⚠️ Главная строка. MemoryMax считает ВСЮ память процесса и потомков, включая нативную
# часть Turbopack — в отличие от предела V8-кучи. При превышении ядро убивает только этот
# срез, редактор и остальные процессы не затрагиваются.
MemoryMax=3G
# Заранее поджимать, не дожидаясь жёсткого предела: рост замедляется, и часто до убийства
# дело не доходит вовсе.
MemoryHigh=2500M
# Своя группа — чтобы `systemctl --user status` показывал, что именно упало и почему.
Slice=dev.slice

[Install]
WantedBy=default.target
```

## Как пользоваться

```bash
systemctl --user daemon-reload
systemctl --user start setfork-dev        # запустить
journalctl --user -u setfork-dev -f       # смотреть лог вместо терминала VS Code
systemctl --user status setfork-dev       # после падения: что случилось и по какой причине
```

Убийство по памяти выглядит в статусе так — это ответ на вопрос «почему упало»:

```
Main PID: … (code=killed, signal=KILL)
Memory: 3.0G (max: 3.0G available: 0B)
```

## Что это даёт и чего не даёт

**Даёт:** падает только сборка, окно редактора живо; видно, что упало именно по памяти, а не
«само закрылось».

**Не даёт:** причину роста. Её ищут снимком памяти отдельно — и до сих пор она не найдена:
замер 22.09 не был доведён до конца, чисел нет. Стенды для него уже созданы — списки
`mem-bench-5 / 30 / 60 / 120 / 240` у пользователя `membench`, то есть повторить замер можно
сразу на пяти размерах.

⚠️ Запускать этот замер **не одновременно с CI**: раннеры живут на той же машине, и
Playwright с браузером тяжелее всего набора тестов. 22.09 три предложения упали красными
именно из-за этого — в логе `The runner has received a shutdown signal`, что выглядит как
чьё-то вмешательство, а не как нехватка памяти.
