# SetFork → GitHub parity: анализ и дорожная карта

Полный разбор «насколько мы уже как GitHub», ключевая архитектурная развилка
**каталог vs список**, и что осталось. Обновлено с учётом того, что **уже построено**
(а построено много — мы фактически на «Уровне 2»).

---

## 1. Где мы стоим сейчас

Тот часто цитируемый анализ делит git-совместимость на два уровня:

- **Уровень 1 — «похоже на git»**: черновик→версия, форк с атрибуцией, диффы. Кастомная
  семантика поверх Postgres.
- **Уровень 2 — «реально git»**: `git clone/pull/push`, настоящая история коммитов,
  стандартный клиент/VSCode.

**Важно: мы уже на Уровне 2.** Список — это настоящий git-репозиторий:

- `git clone https://host/{owner}/{slug}.git` (smart-HTTP, `upload-pack`) — работает из VSCode;
- `git push` создаёт новую версию (`receive-pack` → проекция `list.json` в Postgres);
- **git = источник правды**: персистентный bare-репо на список, SHA запушенных коммитов
  сохраняются; Postgres — проекция для UI/поиска/AI;
- версия = коммит + тег `vN`; auth по API-токену (Basic); `pre-receive` hook валидирует.

То есть «спайк read-only», который советовали сделать сначала, мы уже прошли **и** довели
до записи. Дальнейшее — это не «прыжок на Уровень 2», а **добор фич до полного паритета**.

файловый браузер, релизы-страница, бинарники-в-git. И одна стратегическая развилка ↓

## 3. Ключевая развилка: **каталог vs список**

Вопрос «в основе должен быть каталог, а не list?» — это про то, **где проходит граница
git-репозитория**.

- **GitHub**: единица = **репозиторий** (каталог файлов). Файл — это деталь внутри.
- **SetFork сейчас**: единица = **список** (1 список = 1 репо). Шаги — узлы внутри `list.json`.

### Почему это не косметика
Весь **тезис продукта** — *курирование сообществом*: один канонический список на тему,
его форкают-улучшают, лучший всплывает по звёздам, верификация. Всё это — **пер-список**:
звёзды, форки, verified, issues, диффы версий привязаны к списку.

Если сделать репо = каталог (много списков в одном репо, список = файл), то единицей
курирования станет каталог, а не список — и вся модель «лучший список на тему» ломается
(звёзды на репо-каталог, а не на конкретный список; форк тянет весь каталог).

### Три варианта

**A. Список = репо (как сейчас).**
- ➕ 1:1 с тезисом курирования; уже построено и работает; простая модель прав/звёзд.
- ➖ Связанные списки — разные репо; агенту/человеку надо клонировать много репо;
  нет папок/группировки.

**B. Каталог = репо (список = файл в дереве).**
- ➕ Один `git clone` — весь набор связанных списков; папки; ближе к «настоящему» git-репо;
  агент правит много списков за раз.
- ➖ Ломает пер-список курирование (звёзды/форк/verify/issues становятся пер-репо);
  discovery «лучший на тему» размывается; это **переписывание** модели, а не добор.

**C. Гибрид (рекомендую).** Оставить **список = каноническую git-единицу** (граница репо
не двигается), а «каталог» добавить **как лёгкий слой-оверлей** сверху:
- **Коллекции/каталоги** — именованные подборки списков (свои и чужих) для навигации и
  bulk-действий. Не git-граница, а метаданные (как GitHub Stars-lists / «Collections»).
- **`git clone` каталога** — генерируемый агрегат: репо с submodule/`.gitmodules` или
  «meta-repo», где каждый список подтянут. Агент делает один clone и получает набор —
  **без** переноса курирования на каталог.
- Профиль/овнер = каталог его списков (как страница профиля GitHub со списком репо).

**Рекомендация:** вариант **C**. Курирование хочет list-as-unit — сохраняем (и он уже
работает end-to-end). Каталог даём как discovery/группировку + опциональный агрегат-клон.
Это добор, а не переписывание. Вариант B держим в уме только если продукт сместится с
«канонических списков» на «личные наборы файлов» (другой продукт).

## 4. Дорожная карта до паритета (приоритезированная)

**Фаза 1 — добить git-цикл (агентам важнее всего):**
1. **Коллабораторы** — разрешить push не только владельцу (таблица прав `collaborators`,
   auth в `receive-pack`). Разблокирует командную работу и агентов от имени приглашённых.
2. **Скриншоты шагов в git** — сейчас в S3, `list.json` их не несёт → пуш не меняет.
   Варианты: (а) хранить ссылки на S3 в `list.json` (просто, но бинарь вне git);
   (б) git-LFS. Реком.: (а) сейчас, LFS — потом.
3. ~~**Распределённый лок**~~ — ✅ сделано в ядре: `RepoGuard` = in-process mutex +
   Postgres advisory lock по id списка (setfork-core, `git/repo.rs`).

**Фаза 2 — «каталог»-оверлей (развилка выше, вариант C):**
4. Коллекции/каталоги (метаданные) + страница каталога.
5. Агрегат-клон каталога (submodules/meta-repo).

**Фаза 3 — веб как у репо:**
6. **Файловый браузер дерева** на overview (переключатель «Список ⇄ Файлы»: показать
   `README.md`/`list.json`/`steps/*.md` как дерево с последним коммитом на файл).
7. **Страница релиза** (заметки + ассеты: `.md`/`.html`/`.bundle` уже есть — собрать в
   один Releases-view поверх тегов `vN`).

**Фаза 4 — «настоящие» ветки (самое дорогое, делать только по спросу):**
8. Реальные git-ветки + `merge`. Сейчас — линейный `main`, fast-forward. Ветки требуют
   пересмотра проекции (какая ветка → какая версия) и UI веток/мержа. Большой объём,
   польза неочевидна для «канонических списков». Отложить до явного запроса.

**Низкий приоритет:** SSH-доступ (HTTPS+токен уже покрывает VSCode); orgs/команды.

## 5. Известные напряжения / что решить

- ~~**Одновременная правка через UI и `git push`.**~~ **Снято Ф1 трека git-format
  (2026-07-30):** двойного канона больше нет — веб-правка тоже идёт git-first (коммит
  main в ядре → проекция в Postgres), все пути записи сериализуются одним репо-локом и
  единой точкой обновления main (fast-forward-only, обязательный `list.json`, ADR-0014).
  Ленивая досыпка удалена; при активной двусторонней правке конкурент просто получает
  следующую версию поверх — как и положено линейному main.
- **`list.json` — единственный вход проекции.** Правка `steps/*.md` напрямую пока
  игнорируется (парсер читает только `list.json`). Либо парсить и `.md`, либо явно
  задокументировать «редактируй `list.json`».
- **Бинарники вне git** (см. Фаза 1.2).
- **Прод-требования git-фичи:** бинарь `git` в контейнере + персистентный том `GIT_DATA_DIR`.
- **MCP vs нативный git.** С реальным git агент может `clone`/`commit`/`push` нативно —
  часть работы `mcpUpdateList` становится не нужна. Реком.: MCP оставить для
  поиска/дискавери, редактирование отдавать git там, где агент уже им владеет.

---

## 6. Короткий вывод

Мы **не в начале пути к GitHub — мы уже прошли самую сложную часть** (реальный git с
push, git как источник правды). До ощутимого паритета осталось: **коллабораторы**,
**каталог-оверлей (вариант C)**, **файловый браузер + релизы**. «Настоящие ветки» —
дорого и под вопросом по спросу, откладываем. Единицей курирования оставляем **список**
(это тезис продукта), а «каталог» вводим как слой поверх, а не как новую git-границу.
