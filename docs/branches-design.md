# Ветки для списков — дизайн (фаза A нового плана)

Цель: полный git-набор относительно списков. Ветки → PR-модель → merge с
конфликтами шагов. Этот док — ADR фазы A; живёт и обновляется по мере этапов.

## Модель

- **Ветка = git-ветка bare-репо** (`refs/heads/*`). Источник правды — git, ядро
  (setfork-core) уже владеет refs. **Таблицы branches в Postgres НЕТ** — не
  дублируем состояние (кэш счётчиков добавим только если упрёмся в latency).
- **`main` — канон.** Версии `vN` (строки `template_versions`) проецируются
  ТОЛЬКО из main — как сейчас (`project.rs` читает `refs/heads/main`).
- **Прочие ветки — черновики.** Коммиты в них НЕ создают версий. Это уже так:
  pre-receive hook требует только `list.json` (ветки пропускает), проекция
  смотрит только main → `git push origin my-branch` уже работает как надо.
- **Просмотр на ветке**: страница списка с `?ref=<branch>` материализует tip
  ветки (parse `list.json` + `steps/*.md` — переиспользуем `read_tip`,
  обобщённый на произвольный ref) — read-only рендер, без записи в Postgres.

## Этапы

### A1 — read-only (первый срез)
1. ✅ (уже есть) push в любые ветки принимается, версии не создаются.
2. Ядро: `GitCore.ListBranches(RepoRef)` → `{name, tip_sha, is_default,
   ahead/behind main (счётчики)}`.
3. Ядро: `GitCore.GetBranchSnapshot(RepoRef, ref)` → `{title, desc, tags,
   ordered, steps[]}` — материализация tip ветки (generalized `read_tip`).
4. UI: **селектор веток** в version-bar (слева, как GitHub branch-picker):
   main + ветки с ahead/behind; выбор → `?ref=` → рендер снапшота ветки с
   плашкой «This is branch X — N commits ahead of main».

### A2 — управление ветками
- `CreateBranch(from_ref)` / `DeleteBranch` RPC + кнопки в селекторе.
- Права: ветки может создавать owner/collaborator (те же права, что push).
- Защита main: удалить/переписать main нельзя (hook + проверка в RPC).

### A3 — PR-модель поверх веток
- `suggestions` получают опциональный `branch_ref` (миграция): PR = «ветка →
  main», а не снапшот шагов. Старые снапшот-suggestions продолжают работать.
- Diff PR = diff материализаций (tip ветки vs main) — переиспользуем
  существующий пошаговый diff версий.
- Merge: fast-forward если можно, иначе merge-commit (git2), затем проекция
  новой версии из main (существующий путь). Ветку — предложить удалить.

### A4 — конфликты
- Если main ушёл вперёд и merge конфликтует: наш «merge-режим шагов» —
  трёхстороннее сравнение по шагам (base/ours/theirs), конфликтующие шаги
  выбираются по одному (UI как resolve в редакторе). Результат = merge-commit.

## Что НЕ делаем
- Ветки в Postgres-таблицах (дублирование состояния git).
- Проекция версий из не-main веток.
- Переименование main / изменение дефолтной ветки (пока).

## Открытые вопросы (решаем в своём этапе)
- ahead/behind: считать в ядре через git2 graph — O(коммитов); кэшировать?
- Права на просмотр веток приватных списков — те же, что списка (уже есть).
- Лимит числа веток на список (анти-абьюз) — вместе с квотами фазы C.
